## 0. ГЛАВНОЕ В 10 СТРОК

1. **База ОДНА.** Боевая: `Z:\PTC\CREO-START\plm_reader\db\plm_reader.db` — именно её отдаёт `engine.active_db()`.
2. **Конвейер:** СКАНЕР → база (`origin='real'`) → ДОСТРОИТЕЛЬ (`origin='built'`) → ГРАФ → ПОКАЗ (читает только базу).
3. **Имя модели — по ЕДИНОМУ канону** `creo_read.canon_model`: снять расширение/версию → отсев обрывков → UPPER.
4. **Перескан нужен ТОЛЬКО для данных ИЗ ФАЙЛОВ.** Правки ИМЁН-КЛЮЧЕЙ в базе — это `normalize` + `repair`, **без чтения файлов**, за минуты.
5. **«Фантомы» (висячие) — почти всегда НЕ потеря данных**, а разные записи одного имени (регистр / расширение `.XPR` / обрывок). Лечится каноном, не сканированием.
6. **Архивные таблицы** `changes`, `history`, `arch_dims`, `arch_dim_ch` — НЕ удалять (Purge-safe: это история).
7. **Догма «либо одно, либо другое»:** связь `real` правит СКАНЕР, связь `built` правит ДОСТРОИТЕЛЬ. Никто не лезет в чужое.
8. **Любая операция записи делает БЭКАП** и снимок схемы; ротация бэкапов — всех семейств (`plm_reader_*` и `pre_*`).
9. **Гейт релиза** (`.git/hooks/pre-push`): `selftest` + `verify` + тесты. Без зелёных тестов версия не выкатывается.
10. **Новый модуль/файл обязан попасть в `CODE_FILES`** (`make_version_json.py`), иначе не приедет на шару (грабля V140).

## 1. ОДНА БАЗА (догма «БАЗА — ОДНА»)

- Место боевой базы определяется `engine.active_db()`: приоритет — папка склада, **главный файл — `plm_reader.db`** (не свежайший versioned). Замысел: показ, скан и достройка смотрят в ОДНУ базу.
- Локальная копия инструмента (`D:\AI\tools\agent\plm_reader\db\`) — запасная; её «свежесть» НЕ должна перебивать боевую.
- Переопределить базу можно env-переменной `PLM_DB` (используется в тестах/пробах).
- Версионные файлы `plm_reader_YYYYMMDD_HHMMSS.db` — резерв (ротируются), читаются только если главного нет.

## 2. КОНВЕЙЕР (порядок и авторы записей)

```
1. СКАНЕР            engine.do_scan            файлы склада -> база   origin='real'
2. ДОСТРОИТЕЛЬ       plm_build_links.build     база -> links/derived  origin='built'
3. ГРАФ-ПОСТРОИТЕЛЬ  plm_graph_build.build     база -> graph_nodes/graph_edges/graph_metrics
4. ПОКАЗ             окно PLM / HTML           ТОЛЬКО читает базу (в т.ч. graph_*)
```

- ЕДИНЫЙ источник рёбер — `plm_links.edges()` (читает `links` + `derived`). Второго построения связей НЕТ.
- ПОКАЗ не строит заново — рисует по готовым таблицам графа.

## 3. ЕДИНЫЙ КАНОН ИМЕНИ (`creo_read.canon_model`)

Единственная точка правды для имени модели во ВСЕХ таблицах.

| вход | канон | что произошло |
|---|---|---|
| `er20-a.xpr` | `ER20-A` | снято расширение `.XPR` (V195) |
| `DF.PRT.2` | `DF` | снято расширение и версия |
| `-001-002.PRT` | `` (пусто) | обрывок парсера — не имя модели |
| `abc` | `ABC` | регистр → UPPER |

- Регистр поднимает **Python**, не SQL: в этой сборке SQLite `upper()` — ASCII-only (нет ICU).
- Набор расширений — как в `plm_scanner.path_parts` (`.PRT/.ASM/.DRW/.MFG/.NEU/.SEC/.M_P/.XPR/.TPH/.CRC/.IDX/.STK/.DSN/.MRD/.PDF/.FRM/.LAY`).
- Канон применяют ВСЕ писатели: сканер, достроитель, граф (V193–V196).

## 4. ОПЕРАЦИИ — «что делает / пишет? / читает файлы?»

| Операция (кнопка в окне «Аудит / БД») | Что делает | Пишет в базу? | Читает файлы склада? |
|---|---|---|---|
| **Скан** (`scan`) | читает ФАЙЛЫ → паспорта/параметры/свойства/связи | да (`real`) | **ДА** |
| **Выровнять имена** (`normalize --apply`) | имена-ключи → канон в 25 колонках (`NORM_TARGETS`) | да | нет |
| **Очистить дубли и само-связи** (`repair --apply`) | снять само-связи, дубли, обрывки, пустые ключи | да | нет |
| **Компакт** (`compact`) | обрезка `unknown_fields` до 512 симв. | да | нет |
| **Перестроить граф** (`plm_graph_build`) | graph_nodes/edges по базе | да | нет |
| **Достроить связи** (`plm_build_links`) | обратные связи по базе | да (`built`) | нет |
| **doctor** | read-only диагноз (таблицы, висячие, дубли, диск) | нет | нет |
| **check** | машинная проверка проблем | нет* | нет |
| **VACUUM** | сжатие файла базы | да (файл) | нет |

| **ensure-indexes** | создание индексов | да | нет |

## 5. КОГДА ПЕРЕСКАН НУЖЕН, А КОГДА — НЕТ (ключевой раздел)

### 5.1. ПЕРЕСКАН НЕ НУЖЕН — если дефект про ИМЯ в базе
Признаки: «висячие»/фантомы `params.model`/`links.*`/`derived.*`, разный регистр, расширение в ключе (`.XPR`), обрывки (`-00`, `-001-001.PRT`), дубли, само-связи, «висячие» рёбра графа, расхождение наборов моделей.

**Лечение (за минуты, без чтения файлов):**
1. «Выровнять имена» → `normalize --apply`;
2. «Очистить дубли и само-связи» → `repair --apply`;
3. «Перестроить граф» → `plm_graph_build`.

> После этого база больше НЕ зарастёт: писатели (сканер/достроитель/граф) канонят имена с V196, а `repair` с V202 чистит обрывки.

### 5.2. ПЕРЕСКАН НУЖЕН — если дефект про ДАННЫЕ ИЗ ФАЙЛОВ
- **Изменились ПРАВИЛА РАЗБОРА** (правил `creo_read`/парсеров, `PARSER_TAG`) — формат полей/значений.
- **Появились новые файлы** на складе (или переименование/удаление) — база о них не знает.
- **Изменились КОРНИ или `exclude`** в настройках — другой охват.
- **Нужно добрать данные** (параметры/состав/свойства/история), которых в базе ещё нет.
- **Файлы на складе изменились** (`mtime`), а нужен свежий паспорт/состав.

### 5.3. ТЕСТ-ВОПРОС (правило на всю жизнь)
> «Дефект про **ИМЯ/КЛЮЧ** в базе?» → `normalize` + `repair`.  
> «Дефект про **ДАННЫЕ ИЗ ФАЙЛА** (то, чего в базе нет или разобрано по старым правилам)?» → **скан**.

### 5.4. Частый ложный вывод
> «Выпущена новая версия кода → нужен перескан?» — **НЕТ**, если правка касается канона имён/связей/графа. Новая версия исправит ПИСАТЕЛЕЙ, а старые ИМЕНА в базе — `normalize`. Перескан — только по 5.2.

## 6. ПОРЯДОК ОБСЛУЖИВАНИЯ (чеклист владельца, БЕЗ перескана)

1. **doctor** (read-only) — зафиксировать числа «до».
2. **«Выровнять имена»** (`normalize --apply`) — канон всех ключей.
3. **«Очистить дубли и само-связи»** (`repair --apply`) — само-связи/дубли/обрывки/пустые.
4. **«Перестроить граф»** — узлы-цели рёбер становятся узлами (V197).
5. **doctor** снова — сверить «после» (висячие должны резко упасть).
6. **Только если** после шагов 2–4 остались **РЕАЛЬНЫЕ** висячие (не «регистр/расширение», а отсутствующие модели) — тогда скан.
7. Раз в месяц: `compact` (потолок `unknown_fields`), затем `VACUUM` при необходимости.

## 7. ПРЕДОХРАНИТЕЛИ (почему так, а не иначе)

- **Шара `Z:` — агент только читает.** Разбор идёт read-only: URI `mode=ro` + `PRAGMA query_only=1` (`plm_audit_ro.py`, `doctor`). Команды `check/repair/compact/normalize/vacuum/migrate/ensure-indexes` на `Z:` агент НЕ запускает (они пишут: журнал, кэш, бэкапы, файл базы).
- **Архивные таблицы `changes/history/arch_dims/arch_dim_ch`** — Purge-safe: чистить нельзя (это история). `doctor` делит висячие на «ЖИВЫЕ» и «АРХИВНЫЕ».
- **Бэкапы:** перед любой записью — копия в `db\backup`; ротация всех семейств (`plm_reader_*`, `pre_migrate_*`, `pre_repair_*`, `pre_compact_*`, `pre_normalize_*`) — `engine._rotate_backups`.
- **`journal_mode=DELETE`** предпочтителен (склад SMB). `WAL` оставляет крупные `.db-wal`.
- **Гейт релиза** `pre-push`: `selftest` + `make_version_json --verify` + тесты (`tests/`). Релиз — ТОЛЬКО адресным `git add -- <пути>` / `git commit -- <пути>`.
- **Порядок релиза:** `py_compile` → `selftest` → `verify` → тесты → `APP_VERSION` → `make_version_json` (ПОСЛЕ последней правки файлов!) → коммит.
