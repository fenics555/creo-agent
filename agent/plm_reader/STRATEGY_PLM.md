# STRATEGY_PLM: Дорожная карта модернизации plm_reader

## 🆕 §0.0. АРХИТЕКТУРА V141: Database + SCANNER + CONNECTION + GRAPH (30.10.2026, слово владельца)

> **Слова владельца:** «`Database` = Database (инструмент обслуживает базу данных) → `Scaner — Database`
> + `CONNECTION builder — Database` + `Graph builder — Database`. Все работают **напрямую
> с базой**, наверно чтобы не поломать что-либо: **Scaner пишет в свои ячейки, CONNECTION builder читает все
> НО пишет в свои, Graph builder тоже читает все НО что-то пишет только уже в свои!**»

### §0.0.1. ЧЕТЫРЕ ИНСТРУМЕНТА (роли)

| Инструмент | Роль | ЧИТАЕТ | ПИШЕТ (только своё) |
|---|---|---|---|
| **Database** (Database) | **обслуживание базы, ВЛАДЕЛЕЦ СХЕМЫ** | базу | схему · миграции · индексы · архивы · `meta` |
| **SCANNER** (`engine.py`) | чтение файлов Creo + сверка с базой | **файлы (Z:) + базу** | `snapshots`·`params`·`mass_props`·`dimensions`·`features`·`equations`·`materials`·`history`·`health`·`family`·`folders` |

| **GRAPH BUILDER** (`plm_graph.py`) | граф родословной | базу (ВСЁ) | `graph_nodes`·`graph_edges`·`graph_metrics` |

### §0.0.2. ТРИ ЖЕЛЕЗНЫХ ПРАВИЛА (write-isolation)
1. **Каждый пишет ТОЛЬКО в свои таблицы.** Чужие — только чтение.
2. **Схему меняет ТОЛЬКО Database.** Остальные просят миграцию.
3. **Источник правды — ФАЙЛ (Z:).** База — производная, пересобирается с нуля.

**Почему так:** если сканер и строитель пишут в одну таблицу — **гонка, дубли, порча**.
Это и есть причина, почему раньше «что-то доделывали отдельные скрипты» — **не было границы ответственности**.

### §0.0.3. НОРМАЛИЗАЦИЯ `params` → ПО СУЩНОСТЯМ (30.10.2026)

**Проблема:** `params(path, model, name, type, value)` — **1 135 928 строк «солянки»**:
обозначение, масса, единицы, формат, материал — **в одной куче**.

**Решение — по СМЫСЛУ:**

| Таблица | Что | Откуда |
|---|---|---|
| **`mass_props`** | 🔥 **внутренние `PRO_MP_*` (42 имени)** — масса · объём · площадь · плотность · COG · инерция · TRF · ALT_* | §167 (`e3 32` + 7 байт) |
| **`dimensions`** | 🔥 размеры: **номинал** · допуск · **квалитет** (`tol_class`) · `feat_id` | §173 (`2F B1 B2`) |
| **`features`** | 🔥 дерево: `id` · `feat_defs_<N>` · тип (`pfcFEATTYPE` 314) · статус | §171 |
| **`equations`** | 🔥 уравнения: имя · выражение · тип | **НОВОЕ — не собиралось!** |
| **`materials`** | материал: имя · плотность · описание · тип | `PTC_MASTER_MATERIAL` |
| **`attributes`** | карточка: ОБОЗНАЧЕНИЕ · НАИМЕНОВАНИЕ · ФОРМАТ · ТИП · ПРЕДПРИЯТИЕ | настройки |
| **`units`** | `PTC_UNITS_*` · `PRO_UNIT_*` — служебное | из params |
| `params` | **«прочие параметры»** — ⚠️ **у каждого человека свои и названы по-своему** | как есть |

**⚠️ ОТКРЫТЫЙ ВОПРОС (владелец):** «под другие параметры — у каждого человека свои, названы по-своему — тут я не знаю как быть».
**Предложение:** `params` **оставить как есть** (сырой реестр «имя → значение»), а **поверх** — **настраиваемые
правила** (`settings.json`): «какое имя считать материалом / обозначением / массой». Тогда **чужие имена
не ломают систему**, а правила — **настраиваются без правки кода**.

### §0.0.4. УРАВНЕНИЯ — СОБИРАТЬ ВСЕ (30.10.2026)

**Владелец:** «Почему только `_des_from_rel` и прямо в движке, а не настройками? **Уравнения нужно
собирать ВСЕ** — и в основном окне уравнений, и в окне **«пострегенерации»** (там обычно `MASS=PRO_MP_MASS`,

```
**⇒ «Что изменилось после регенерации» ЧИТАЕТСЯ ИЗ ФАЙЛА** (`chg_param_arr` + `old_state`→`new_state`).

### §0.0.5. БЕСШОВНОЕ ОБНОВЛЕНИЕ (GitHub)

**Владелец:** «ДРУГИЕ ЛЮДИ ЧЕРЕЗ GITHUB ТАКЖЕ ОБНОВЛЯЮТСЯ!!! т.е. нужна **бесшовное обновление**!»

**Решения:**
1. **`schema_version` в `meta`** — при старте сверка; **Database мигрирует шаг за шагом** (вверх).
2. **База НЕ в Git** (1.25 ГБ, у каждого своя) — только **код и схема**.
3. **Обратная совместимость:** новая версия читает старую базу; **миграция только вверх**.
4. **`PARSER_TAG`** — при смене правил парсинга: старые строки помечаются, **перечитываются**.
5. **`settings/settings.json` НЕ перезаписывается** при обновлении (пользовательские правила).
6. **`db/backup/`** — Database делает **бэкап перед миграцией**.

## ⚖️ ГЛАВНОЕ ПРАВИЛО ЧТЕНИЯ ЭТОГО ДОКУМЕНТА (слово владельца, 23.10.2026)

1. **СТАРШИНСТВО ПО ВРЕМЕНИ.** У подсказок есть **дата/время создания и правки**. **Более свежая
   подсказка ПЕРЕКРЫВАЕТ старую** — читать по убыванию свежести. Актуальные: **№15** (23.10.2026
   **12:32**) → **№14** (23.10.2026 **10:09**) → №10–13 (23.10.2026 09:19–10:01) → №7–9 (23.10.2026
   08:55–09:16) → №1–6 (21.10.2026) → `PODSkAZKA1–6` (20–21.10.2026 — самое старое).
   **Вывод:** слова «противоречие между №14 и №15» — ОШИБКА. Правильно: №15 **новее** и является
   РАЗВИТИЕМ №14 (владелец попросил HTML-панель → №15 её добавил). Смотреть как эволюцию, не как спор.
2. **НО ПОДСКАЗКА ≠ ФАКТ.** Подсказка — версия (может быть устаревшей, ошибочной, обрезанной или
   написанной под воображаемый код). **Факт — только живое чтение файла/кода.** Если свежая подсказка
   противоречит коду — **источник истины код** (+ оговорка владельца).
3. **ИЩИ ЛУЧШИЙ ВАРИАНТ.** «Свежая подсказка» — не обязательно лучшая: возможен вариант точнее,
   проще, дешевле или прямой отказ от её подхода. Решение фиксировать с обоснованием.
4. **ФОРМАТ ССЫЛКИ:** файл + место (раздел/строка) — чтобы правку можно было проверить, не читая
   подсказку целиком.

   │ с разными настройками вывода              │
   └──────────────────────────────────────────┘
```

### Четыре правила, из которых всё следует

1. **СКАНЕР ОДИН.** Читает **ФАЙЛЫ в лоб** — **всё, что может**, пишет в **ЕДИНУЮ базу**, включая
   `links` (`real`). Второго входа скана быть не должно; режимы — **существующие галочки** окна
   (`full` = «перечитать всё», `latest_only` = «только последние версии», `recurse`, `depth`, `max_size_mb`,
   `auto_refresh`, `show_limit`, `purge_keep` — реестр из 8 ключей группы СКАН).
2. **ПОСТРОИТЕЛЬ читает БАЗУ, не файлы.** Выстраивает **обратные** связи в `links` (`built`):
   потомок знает родителя — родитель не в курсе; сборка знает компонент — компонент не знает сборку.
   Идемпотентно, реальную связь не дублирует, из окон автоматически не запускается.
3. **ГРАФ ОДИН.** Полный единый граф строится по `links` (`real`) + `links` (`built`).
   Одно построение рёбер — `plm_graph.plm_edges()`.
4. **ПОКАЗ ТОЛЬКО ПОКАЗЫВАЕТ.** Окна (основное / HTML) выводят **из ЕДИНОЙ базы** и **не читают файлы Creo**.

### ПРЕВЬЮ — часть СКАНА, а не отдельный проход

> Вопрос владельца: «Скан же должен и превью собирать, если оно читается в лоб???
> Или нужно как-то повторно сканировать чем-то?»

**Ответ: превью собирает СКАН. Повторно сканировать ничем не нужно.**

- Сканер **уже читает файл в лоб** → превью для него **побочный продукт того же чтения**.
- Читать файл дважды (сканером и потом графом) — **запрещено**: один файл — одно чтение (одна правда).
- **ФАКТ «до» (28.10.2026):** вырезка превью живёт в **`plm_graph.py`**
  (`_media_cache_path` стр. 86, `_load_media_cache` 90, `_save_media_cache` 107, `collect_by_path` 137,
  `collect_from_db` 432, `collect_from_snapshots` 644) — **показ лазит в файлы** и режет картинки.
- **ФАКТ «после» (цель):** вырезка переезжает **в сканер**; `db\media\` + `db\media_cache.json`
  пишутся скан-проходом; граф и окна **только читают** готовое.
- **Побочная выгода (наблюдение владельца):** один скан вместо нескольких блоков → **время
  сканирования должно сократиться** (файл читается один раз, из него берётся сразу всё).

## 5. 5-слойная модель постоянных данных
Граф должен быть структурирован на пять различных типизированных слоев, отражающих реальный производственный процесс:

| Слой | PLM Класс | Биологический/Физический аналог | Бинарный якорь / Сигнатура |
| :--- | :--- | :--- | :--- |
| **Уровень 1** | **КД Мастер** | "Идеальный" проект | `FeatDefs` (чистая геометрия) |
| **Уровень 2** | **Деталь-Заготовка (_Z)** | "Черновая" деталь мехобработки | `MERGE_BASE_PART` (Наследование) |
| **Уровень 3** | **Деталь-Отливка (_O)** | "Расплавленный" металл | `PTC_SHRINKAGE_FACTOR` (Усадка) |
| **Уровень 4** | **Мастер Оснастки (MSTR)** | "Форма" (Шаблон) | `Parting_Surface` / `Core_Print` |
| **Уровень 5** | **CAM-Процесс (ASM_MFG)** | "Заводские" инструкции | `FullMData` (Скорости/Подачи/Траектория) |

**Логика связей:**
- **BOM (Сверху-Вниз):** Сборка $\to$ Компоненты (через `NeuAsmSld`).
- **Генеалогия (Снизу-Вверх):** Компонент $\to$ Мастер (через `MERGE_BASE_PART` в `FeatDefs`).

### 5.1. 🔴 РАЗБОР ВОПРОСА ВЛАДЕЛЬЦА: «зачем отдельные блоки?» (28.10.2026)

> Вопрос: «`inherit` / `asm_comp` / `family` / `plm_tree` — это же всё в `links` (`real`) читается
> либо в `links` (`built`), зачем отдельные блоки?»

**Проверено фактом поиском по коду (`INSERT INTO <таблица>`, 28.10.2026):**

| Таблица | Кто ПИШЕТ | Кто ЧИТАЕТ | Вердикт |
|---|---|---|---|
| `inherit` | **никто** (0 вхождений) | `plm_links.py`, `plm_queries.py` | **призрак** → в `links` |
| `asm_comp` | **никто** (0) | те же | **призрак** → в `links` (состав = `parent`/`child`/`qty`) |
| `plm_tree` | **никто** (0) | те же | **призрак** → в `links` (представление дерева, не источник) |
| `derived` | `engine.py:2072` (сканер)<br>`plm_build_links.py:85` (построитель) | `engine.py` (4), `plm_links.py` (1), `plm_queries.py` (1) | **живёт** — но нужна колонка `kind` |
| `family` | `engine.py:2156` (сканер) | те же | **живёт ОТДЕЛЬНО** — это не связь |

**Почему `derived` нельзя просто выбросить в `links`.** Факт `engine.py:957`:
`links(parent, child, qty, source)` + миграцией `origin`. **ВИДА связи там НЕТ.** А в `derived` он есть —
колонка `kind`: заготовка / отливка / отражение / мастер-модель. Потерять нельзя (догма §95:
наследоваться может модель, материал, свойство, вспомогательная геометрия).

**Решение:** **вид связи — отдельная колонка `kind` в `links`**. Тогда **одна `links`** несёт связь,
её вид (`kind`) и происхождение (`origin` = real/built). Отдельная `derived` становится не нужна.

**Почему `family` остаётся.** Это **не связь изделий**, а **модель данных Creo**: генерик → исполнения
с параметрами (таблица семейства). Связь «родитель–потомок» её не выражает — это другой класс данных.

**Итог: было 6 таблиц-«блоков» связей → остаётся ОДНА `links` (`parent`, `child`, `qty`, `source`, `origin`, `kind`).**
