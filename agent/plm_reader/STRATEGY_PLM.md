# STRATEGY_PLM: Дорожная карта модернизации plm_reader

## 1. Краткое резюме
Текущий набор инструментов `plm_reader` успешно установил способность парсить контейнеры Creo UGC и генерировать функциональный граф зависимостей. Однако, чтобы перейти от "инструмента для исследований" к **готовому для промышленной эксплуатации (Enterprise) движку PLM**, он должен принять строгую, многослойную и устойчивую архитектуру.

Эта дорожная карта, основанная на инженерном анализе Gemini "PODSKAZKA" (подсказки 1-15), описывает эволюцию от базового парсера к полноценному **Оркестратору Жизненного Цикла и Цифровых Двойников**.

---

## 2. Видение: Ядро корпоративной PLM-системы
Цель — перейти от простого "чтения файлов" к **"Управлению Состояниями и Связями"**.
- **От Файлов к Сущностям:** Вместо простого чтения файлов мы управляем *Сущностями* (Детали, Сборки, Техпроцессы, Отливки).
- **От Статики к Динамике:** Вместо одиночного снимка (snapshot) мы управляем *Версиями* (Снимки + дельта-мутации).
- **От Локального к Интегрированному:** Вместо локального графа мы генерируем *Стандартизированные Пакеты Данных* (XML/JSON) для систем ERP (1C:ERP) и PLM (Windchill/Teamcenter).

---

## 3. Технический фундамент (Правила игры)

Для обеспечения 100% надежности в гетерогенной среде (Windows/SunOS) должны быть внедрены следующие системные инварианты:

### 3.1. Архитектурная устойчивость
- **Динамическое определение эндианизма:** Каждый парсер ОБЯЗАН определять архитектуру хоста через заголовок `# - MACH`.
  - *Windows/Little-Endian:* `<`
  - *SunOS/Big-Endian:* `>`
  - **Источник:** `PODSkAZKA от ГЕМИНИ11.MD`
- **Точность бинарного доступа:** Использовать 16-битные относительные смещения (`uint16`) для таблиц маппинга (`id_map_info_ptr`), чтобы избежать ошибок Out-of-bounds в больших файлах.
  - **Источник:** `PODSkAZKA от ГЕМИНИ14.MD`

### 3.2. Целостность данных и локализация
- **Приоритет кириллицы при работе со строками:** Пул `LargeText` должен парситься со строгим декодером `CP1251`, с переходом на `latin-1` только при необходимости. Это критически важно для российских стандартов ГОСТ и имен конструкторов.
  - **Источник:** `PODSkAZKA от ГЕМИНИ1.MD`, `PODSkAZKA от ГЕМИНИ11.MD`
- **Дедупликация медиафайлов:** Внедрить хэширование SHA-256 для всех встроенных изображений (JPEG из `.prt`/`.asm`, BMP из `.drw`), чтобы предотвратить раздувание базы данных PLM.
  - **Источник:** `PODSkAZKA от ГЕМИНИ14.MD`

## 4. 5-слойная модель постоянных данных
Граф должен быть структурирован на пять различных типизированных слоев, отражающих реальный производственный процесс:

| Слой | PLM Класс | Биологический/Физический аналог | Бинарный якорь / Сигнатура |
| :--- | :--- | :--- | :--- |
| **Уровень 1** | **КД Мастер** | "Идеальный" проект | `FeatDefs` (чистая геометрия) |
| **Уровень 2** | **Деталь-Заготовка (_Z)** | "Черновая" деталь мехобработки | `MERGE_BASE_PART` (Наследование) |
| **Уровень 3** | **Деталь-Отливка (_O)** | "Расплавленный" металл | `PTC_SHRINKAGE_FACTOR` (Усадка) |
| **Уровень 4** | **Мастер Оснастки (MSTR)** | "Форма" (Шаблон) | `Parting_Surface` / `Core_Print` |
| **Уровень 5** | **CAM-Процесс (ASM_MFG)** | "Заводские" инструкции | `FullMData` (Скорости/Подачи/Траектория) |

**Логика связей:**
- **BOM (Сверху-Вниз):** Сборка $\to$ Компоненты (через `NeuAsmSld`).
- **Генеалогия (Снизу-Вверх):** Компонент $\to$ Мастер (через `MERGE_BASE_PART` в `FeatDefs`).
- **Производство (Процесс $\to$ Инструмент):** CAM $\to$ Приспособление/Станок (через `id_map_info_ptr`).

**Источник:** `PODSkAZKA от ГЕМИНИ6 -цепочки связей.MD`, `PODSkAZKA от ГЕМИНИ9.MD`
